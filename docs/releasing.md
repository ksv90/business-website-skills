# Публикация

Conventional Commits → Release Please PR → одобренный
merge → тег/Release → ZIP, установщики и SHA-256 из содержимого тега. Архивы содержат только переносимые
скиллы, без Git, workflow, тестов, баз клиентов и вспомогательной сборочной среды.

## Первое размещение

1. Владелец просматривает исходники и проверки, затем явно разрешает нужные Git-действия.
2. Создать GitHub-репозиторий в выбранном владельцем аккаунте с выбранной видимостью,
   настроить remote и отправить одобренное содержимое в main. Не считать эту инструкцию
   поручением выполнить команды; создание локальной папки не создаёт GitHub-репозиторий.
3. В GitHub Actions разрешить создание pull request. По необходимости настроить
   RELEASE_PLEASE_TOKEN через секреты репозитория; обычный GITHUB_TOKEN используется
   как запасной вариант. Права: contents/issues/pull-requests write для release job.
4. Проверить CI. Первый feature commit запускает подготовку Release Please PR;
   проверить предложенную начальную версию 1.0.0 и общий version.txt вместе с обоими SKILL.md.
   Manifest 0.0.0 — исходное состояние до первого выпуска, не текущая версия архива.
5. Выпуск версии, merge release PR и создание/отправка тегов требуют явного поручения
   владельца. После одобренного merge Release Please обновляет manifest и публикует.

Если нужен вручную подготовленный первый выпуск, согласовать его отдельно, выставить
manifest и changelog в соответствии с реальным выпуском и создать одобренный тег на main.
Затем можно явно запустить Repair release assets для этого существующего тега. Workflow
не создаёт новый Git-тег и отклоняет тег вне main либо несовпадающую версию.

## Почему upload в том же workflow

Проверки запускаются при push в main и вручную, без события pull_request — как в
slot-game-ui-skill. После успешных проверок main Release Please автоматически создаёт
или обновляет release PR. Отдельный запуск CI для этого PR и его подтверждение
«Approve and run» не нужны. Слияние release PR остаётся отдельным действием владельца.

Выпуск с GITHUB_TOKEN не должен зависеть от нового события release.published для сборки:
такая цепочка может не запуститься. После release_created используется checkout точного
тега и upload в том же job. Это также не позволяет случайно упаковать более свежий main.

## Версии и совместимость

Используется общий SemVer. Release Please обновляет version.txt и помеченные строки в обоих
SKILL.md; валидатор требует совпадения. Изменение схемы handoff/таблицы рассматривается
отдельно от версии инструкции. Ломающие изменения описываются явно с миграцией.

После выпуска проверить восемь assets: два ZIP, install.sh, install.ps1 и четыре файла
SHA-256. Установщики получают номер версии при сборке и скачивают архивы именно её.
Не размещать исходные установщики с незаполненным маркером версии вместо файлов из dist.
Скачать assets в чистую папку, сверить SHA-256,
структуру и независимую установку каждого скилла. Repair workflow может заменить assets
существующего релиза, поэтому его запуск тоже должен быть осознанным поручением.
Факт локальной сборки или конфигурация workflow не доказывают работоспособность GitHub CI.
