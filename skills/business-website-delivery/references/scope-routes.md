# Scope and implementation routes

Choose by visitor tasks and operating needs, not by the most elaborate available stack.
Use current official documentation for selected frameworks, integrations and hosting.
Do not hard-code provider prices or API promises into this skill.

| Route | Suitable need | Concrete deliverables | Additional launch conditions |
| --- | --- | --- | --- |
| landing | One business, compact service offer, call/write/request | Responsive page, editable data, contacts, optional form | Verified contacts and deployment |
| multi_page | Distinct services, locations, meaningful content depth | Route/content model, navigation, metadata, reusable sections | Content ownership, redirects if replacing site |
| catalogue | Products/services with browsing but no checkout | Categories, detail pages, filters, source of updates | Current catalogue and import/update process |
| booking | Time/resource reservations | Availability source, booking states, cancellation policy | Real provider, timezone, conflicts, duplicate protection |
| commerce | Orders and payments | Catalogue/cart, checkout, order lifecycle, receipts/integration | Payment merchant setup, refunds, stock and fulfilment |
| custom | Accounts, workflows, dashboards, portals | Role/data model, scoped vertical slice, operations plan | Authorization, privacy, monitoring, recovery |

“Turnkey” includes agreed deployment, handover and operations responsibilities. It does
not mean silently supplying unbounded revisions, content, traffic acquisition or support.
For larger scopes write a feature matrix: included, excluded, deferred, unresolved;
acceptance criteria; dependencies; delivery milestones; ongoing costs and ownership.

Implement high-risk integration assumptions early in a sandbox. For custom applications
validate one end-to-end task before expanding screens. Model loading, empty, error,
unauthorized and ambiguous outcomes. Do not sell a clickable mockup as a working system.

## Template strategy

Start with one niche archetype per validated need, not hundreds of speculative templates.
Store a template profile: intended niche/visitor action, available sections, required
facts/assets, stack, accessibility considerations and tested viewports. Keep stable
layout/components separate from company content, theme tokens and integration settings.

Personalization includes service hierarchy, copy, CTA, imagery and local context—not
only changing the logo and name. A useful reusable example is a repair template with
problem/service selection and quote request; a studio may emphasize portfolio and
appointment. These sections are candidates, not mandatory blocks.

Avoid mass-producing near-identical local pages for SEO. Multi-location pages need real
branch-specific value and verified contacts. Never clone a competitor's branded design,
copyrighted copy or business identity.

For a first landing page prefer the simplest stack compatible with existing tooling and
the required forms/editing/deployment. Introduce CMS only when editorial needs justify it.
Avoid a custom backend when a suitable authorized service meets the agreed requirements.
